1. PyTorch / BGE-M3 全局单例多线程推理冲突
--------------------------------------------------------------------------------
- 【现象】：多文件并发上传时，程序在 node_bge_embedding 节点突然崩溃，抛出异常：
  "NotImplementedError: Cannot copy out of meta tensor; no data! Please use torch.nn.Module.to_empty() instead of torch.nn.Module.to() when moving module from meta to a different device."
- 【成因】：BGE-M3 推理模型在 Python 内部采用全局单例。由于 FastAPI 后台任务（BackgroundTasks）运行在同一个进程的 ThreadPoolExecutor（多线程）中，多个解析线程在同一时刻并发调用 `model.encode_documents`。在 PyTorch 底层，这会导致多线程同时对同一个模型实例进行设备状态拷贝（`to(device)`）或者操作延迟加载的 meta tensor，引发线程不安全的严重竞争冲突。
- 【对策】：在模型封装客户端中引入 `threading.Lock()`。在获取模型并执行推理的临界区添加排队互斥锁保护：
  ```python
  import threading
  bge_model_lock = threading.Lock()

  def get_bgem3_embedding(texts):
      with bge_model_lock:
          model = get_bgem3_model()
          embeddings = model.encode_documents(texts)
      return embeddings
  ```

2. Milvus 多线程并发建表冲突
--------------------------------------------------------------------------------
- 【现象】：在系统部署初期或首次上传多个文件时，后台解析报错中止，提示 Collection 冲突或已存在（CollectionAlreadyExists）。
- 【成因】：在数据持久化节点，各线程在写入前先检测 `has_collection`。在并发执行下，多个线程在同一微秒发现 Collection 不存在，并几乎同时触发 `create_collection`。由于建表在 Milvus 端是非原子的，导致其中一个线程因创建同名集合而崩塌。
- 【对策】：采用“线程互斥锁 + 异常忽略”的双层防线设计：
  1. 使用 `threading.Lock` 限制同一时刻仅允许一个线程检测并建表；
  2. 对建表动作包裹 `try...except`，若由于多进程并发或其他因素导致集合已存在，优雅拦截异常，记录 Warning 并不向上抛错，保证 insert 流程的幂等与高并发安全性：
  ```python
  with milvus_lock:
      if not client.has_collection(chunk_collection):
          try:
              client.create_collection(chunk_collection, schema, index_params)
          except Exception as e:
              if "already exists" in str(e).lower():
                  logger.warning("Collection已存在，忽略并发建表异常")
              else:
                  raise e
  ```

3. PyMongo 链式 sort() 调用覆写导致排序失效
--------------------------------------------------------------------------------
- 【现象】：读取历史对话时，取到的不是最新 3 条并按时序升序排，而是取到了数据库中最老的几条数据。
- 【成因】：PyMongo 游标（Cursor）为延迟计算的声明式语法。当进行如下链式调用时：
  `collection.find(...).sort("ts", -1).limit(limit).sort("ts", 1)`
  后调用的 `.sort("ts", 1)` 会完全重置并覆盖先调用的 `.sort("ts", -1)`，导致整个查询降级为“直接按升序查出最老的 limit 条记录”。
- 【对策】：先以降序查出最新 `limit` 条记录并转化为 Python 内存 `list`，再在 Python 内存中使用 `.reverse()` 或是切片反转顺序，实现完美正序排列：
  ```python
  res = list(collection.find({"session_id": session_id}).sort("ts", -1).limit(limit))
  res.reverse()
  return res
  ```

4. 普通图片超链接无法在前端显示（超链接转换与空格截断）
--------------------------------------------------------------------------------
- 【现象】：大模型从 RAG 参考内容中带出含有空格的图片超链接如 `[Slide 4](http://.../my image.jpg)` 时，前端只渲染出普通超链接，用户需要点击或复制才能看图。此外，URL 内部有空格时会被 marked 解析器在空格处截断，导致无法访问；直接用正则做图片包装时又容易误伤已有的 Markdown 超链接，导致嵌套错误。
- 【对策】：在 `formatAnswerToHtml` 前端 Markdown 转换前设计一套鲁棒的“第 0.5 步预处理”正则体系：
  1. 使用 `rawImgWithSpaceRegex` 检测含空格图片链接，将其中空格替换为 `%20`，杜绝截断；
  2. 使用带负向回溯断言且包含非右括号匹配的 `imgLinkRegex`，智能识别以常见图片后缀结尾的普通超链接并重构为 Markdown 图片格式，直接在前端渲染为 `<img>`，免除用户点击：
  ```javascript
  // 识别普通链接格式中其实指向图片的链接，自动转换为 Markdown 图片语法
  // 使用 (?<!\!) 排除已经带 ! 的，并用 [^)] 支持 URL 内部有空格的链接
  const imgLinkRegex = /(?<!\!)\[(.*?)\]\((https?:\/\/[^)\u007f-\u009f]+?\.(?:png|jpe?g|gif|webp|bmp|svg)(?:\?[^)#]*)?)\)/gi;
  mdText = mdText.replace(imgLinkRegex, (match, text, url) => {
      return `![${text}](${url})`;
  });
  ```

5. 中置信度 SSE 澄清文本不渲染
--------------------------------------------------------------------------------
- 【现象】：后端检索出多个中置信度候选产品，在 MongoDB 中已经写入了澄清话术，但在前端界面没有任何文本出现。
- 【成因】：后端触发直接回答澄清时，向前端 SSE 推送了带有 `"event": "progress"` 的数据。然而，前端 app.js 监听器中定义 `progress` 事件仅用于更新页面顶部进度指示器，并不渲染消息文本气泡（文本仅在 `delta` 事件中被追加渲染）。
- 【对策】：修改后端 node_answer_output 触发中置信度文本时的事件类型为 `"delta"`，以让前端顺利接收并更新聊天气泡。

6. Marked.js 第三方库初始化报错崩溃
--------------------------------------------------------------------------------
- 【现象】：前端聊天页面开启后，所有消息都降级为了纯文本，Markdown 表格、图片、超链接样式全部失效。浏览器控制台报错：`TypeError: Je is not defined`。
- 【成指】：本地的 `marked.min.js` 文件被进行了非标准的语法修改，破坏了原有的 UMD 打包闭包环境，导致 marked 无法挂载在全局 `window` 上。
- 【对策】：通过官方 CDN 重新下载标准无损的 UMD 版 `marked.min.js` 完整覆盖并解决。

7. MongoDB 内存排序限制（In-Memory Sort 32MB Limit）引发的系统崩溃
--------------------------------------------------------------------------------
- 【现象】：在高并发对话读取或单个会话对话历史数量过多时，MongoDB 突然报错拒绝服务：
  "Executor error during find: Sort stage used more than maximum allowed RAM of 33554432 bytes. Write a temporary file or increase the buffer size."
- 【成因】：MongoDB 在对查询结果执行 `.sort()` 排序时，如果排序字段没有匹配的索引，引擎需要在内存中将检索出的文档进行临时排序。为了保证数据库服务稳定性，MongoDB 在物理上设置了 **32MB 的排序内存上限**。一旦某次查询所需排序的文档总大小超过 32MB，查询就会被数据库引擎强制中断抛错。
- 【对策】：
  1. 建立匹配的**复合索引（Compound Index）**：在数据库中为过滤字段与排序字段建立联合索引，例如：`[("session_id", 1), ("ts", -1)]`；
  2. 实现索引覆盖排序（Indexed Sort）：通过该索引，MongoDB 可以按照已经按顺序物理排好的 B+Tree 索引结点直接读取数据返回，不需要在运行时内存中做任何额外排序处理，从根本上杜绝了 32MB 内存爆表的隐患。

9. [Bug 9] Python 字符串 format() 大括号占位符 KeyError 报错冲突
================================================================================
- 症状：
  后端 RAG 生成节点的 ANSWER_PROMPT 中为了引导模型输出，指定了 "{[chunk_id]}" 格式的范例。在执行 prompt.format(context=...) 时，系统崩溃抛出 KeyError: 'chunk_id'。
- 原因：
  Python 的 str.format() 函数默认会将大括号 "{}" 包裹的内容（如 "{chunk_id}"）识别为格式化替换变量。如果传入的参数中没有对应的 key，则会触发 KeyError。
- 解决：
  - 方案一：在 Prompt 文本中，通过双写大括号进行转义，写为 "{{[chunk_id]}}"。
  - 方案二（推荐）：放弃大括号，统一改用双中括号形式表示引用标注，即 "[[chunk_id]]"。这样不仅完全绕过了 format() 的解析限制，更利于大模型稳定输出，前端正则直接匹配 "/\[\[(\d+)\]\]/g" 解析点击角标，更为干净鲁棒。

10. [Bug 10] Cross-Encoder Reranker 数据清洗时丢失原始召回元数据 Bug
================================================================================
- 症状：
  RAG 点击引用角标后，右侧抽屉展示的 "来源文件" 显示为 "local"，且 "参考小节" 总是显示为对应的大标题（如 "HAK180烫金机"），无法具体追溯章节。
- 原因：
  在 node_rerank.py 节点中，混合本地和网页召回后，在 get_rerank_docs 方法内进行了统一的数据清洗（cleaned_docs），把所有召回块规整成了含有 title, content, source, url 键的简易字典。而原始本地召回字典中含有的 file_title (原文件名) 和 section_title (原章节段落名，对应的 key 是 "title") 元数据在此阶段被全部丢失，导致后续生成和推送给前端的 chunks 无法定位展示。
- 解决：
  - 在 node_rerank.py 重排清洗时，主动追加保留这两个重要的元数据键名：
    "file_title": doc.get("file_title"),
    "section_title": doc.get("section_title")  # 对应本地小节标题
  - 随后在生成节点推送 chunks 时，优先读取 file_title 和 section_title 字段并使用 source 和 title 作为 fallback：
    "file_title": chunk.get("file_title") or chunk.get("source"),
    "section_title": chunk.get("section_title") or chunk.get("title")

11. [Bug 11] 大模型因标注 [[idx]] 引用角标而选择合并、替代输出正文图片的逻辑缺陷
================================================================================
- 症状：
  如果参考的知识库分块（Chunk）中同时包含了文字说明和图片链接（MinIO URL），在模型生成回答时，虽然它正确在陈述末尾加了引用标注如 `[[1]]`，但本应直接在正文输出以渲染展示的图片链接却被大模型合并替代掉了（模型觉得既然标了角标说明来源，图片自然也包含在来源中，用户去右侧抽屉里看就行了，因此为了省事而不直接打印图片链接）。
- 原因：
  提示词约束不足。在没有硬性强调的情况下，大模型会自动对“直接显示图片”和“标注引用角标”这两个重合的意图进行合并和精简，导致图片缺失，极度影响页面直观的用户体验。
- 解决：
  - 在 `config.py` 的本地会话提示词中强力加入限制：
    “（注意：图片引用的优先级最高！如果被参考的内容中包含真实的图片链接，你必须严格在相关的文字段落下方单独起一行直接引用并输出图片 URL，绝对不能因为标注了 [[idx]] 角标而省略输出图片链接！）”
  - 从 Prompt Engineering 层面为模型划定这两者的边界和优先级，完美实现了角标和图片的共存。
